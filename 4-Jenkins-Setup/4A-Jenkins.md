# Jenkins Pipeline Plan

Goal: first design the Jenkins flow before writing Jenkinsfiles. The app code and Kubernetes config will stay separate. A pipeline should deploy only the selected service, not the whole system every time.

Main parameters for manual deploy jobs:

- `SERVICE`: `frontend`, `user-service`, or `todo-service`
- `ENV`: `staging` or `production`
- `BRANCH`: usually `release/3.40`
- `IMAGE_TAG`: generated by the pipeline, not typed manually

Version is not a separate parameter. It is derived from the release branch name.

Example:

```text
BRANCH=release/3.40
VERSION=v3.40
SERVICE=todo-service
COMMIT=abc1234
STAGING_IMAGE=todo-service:abc1234-v3.40-staging
PROD_IMAGE=todo-service:abc1234-v3.40-prod
```

---

## 1. Feature Branch Pipeline

Trigger:

```text
feature/* branch push
```

Question:

```text
Does this developer's change work by itself?
```

Actions:

- Checkout the pushed feature branch.
- Run linting.
- Run static code analysis.
- Run unit tests.
- Do not deploy.
- Do not create a production/staging image.

Unit tests should run inside a prepared Jenkins test container image. This image contains the common CI tools, but not each service's application requirements.

Example CI image content:

```text
python
pip
venv
pytest
pytest-cov
black / flake8 / ruff
git
curl
build tools needed by Python packages
```

Service dependencies are handled with a persistent venv cache.

---

## 2. Venv Cache For Unit Tests

The Jenkins Kubernetes agent mounts a PVC, for example:

```text
/cache/venvs
```

For every service, the pipeline calculates a cache key from:

- service name
- Python version
- CI image version
- hash of `requirements.txt`

Example:

```text
/cache/venvs/todo-service-py3.11-ci-v1-a82f19c
/cache/venvs/user-service-py3.11-ci-v1-b31d9aa
```

If that venv already exists, Jenkins activates it and runs tests directly:

```bash
source /cache/venvs/todo-service-py3.11-ci-v1-a82f19c/bin/activate
pytest
```

If it does not exist, Jenkins creates it once:

```bash
python -m venv /cache/venvs/todo-service-py3.11-ci-v1-a82f19c
source /cache/venvs/todo-service-py3.11-ci-v1-a82f19c/bin/activate
pip install -r App/todo-service/requirements.txt
pytest
```

If `requirements.txt` changes, the hash changes and a new venv is created. This is the cache invalidation rule.

This replaces the old `Dockerfile.test` approach for unit tests.

## 3. Pull Request Pipeline

Trigger:

```text
feature/* -> release/* pull request opened or updated
```

Question:

```text
Will this feature work with the target release branch?
```

Actions:

- Checkout the PR merge result if possible.
- Run linting.
- Run static code analysis.
- Run unit tests with the same venv cache mechanism.
- Do not deploy.

This protects the release branch before accepting the PR.

---

## 4. Release Branch Pipeline

Trigger:

```text
PR merged into release/*
```

Question:

```text
Is this release branch commit ready to become a deploy candidate?
```

Actions:

- Checkout the updated release branch.
- Run linting.
- Run static code analysis.
- Run unit tests.
- Later: run integration or e2e tests.
- Mark this commit as a successful release candidate.

This pipeline is needed because the branch can change between PR creation and PR merge. Another PR may have been merged first.

The manual staging deploy must check that the selected commit has a successful release branch pipeline result.

---

## 5. Manual Staging Deploy Pipeline

Trigger:

```text
Jenkins Build with Parameters
```

Parameters:

```text
SERVICE=todo-service
ENV=staging
BRANCH=release/3.40
```

Rules:

- Derive version from `BRANCH`.
- Resolve the exact commit SHA from the branch.
- Check that this commit passed the release branch pipeline.
- Build only the selected service's production Docker image.
- Push the image to GHCR.
- Update/apply only that service's staging manifest.

Image tag format:

```text
<service>:<commit>-v<release-version>-staging
```

Example:

```text
todo-service:abc1234-v3.40-staging
```

This job should not repeat all unit tests if the selected commit already has a successful release branch pipeline result.

Staging e2e tests can be a separate pipeline later. Production deploy can require that staging e2e pipeline to be green.

---

## 6. Manual Production Deploy Pipeline

Trigger:

```text
Jenkins Build with Parameters
```

Parameters:

```text
SERVICE=todo-service
ENV=production
BRANCH=release/3.40
```

Rules:

- Do not rebuild the image.
- Find the exact staging image digest.
- Retag the same digest with the production tag.
- Push the production tag.
- Deploy that exact image to production.
- Run a small smoke check after deploy.
- After production is successful, merge the release branch back to `main`.

Image promotion example:

```text
todo-service:abc1234-v3.40-staging
todo-service:abc1234-v3.40-prod
```

The important rule: production uses the same artifact that was tested in staging.

---

## 7. Why Not Rebuild For Production?

Staging should test the exact image that will go to production. If production builds again, then production may receive a different artifact even if the source commit is the same.

Correct flow:

```text
build once -> deploy staging -> approve -> retag same digest -> deploy production
```

This is immutable artifact promotion.

---

## 8. Branch And Version Rules

Release branch naming:

```text
release/3.40
release/3.41
```

Version extraction:

```text
release/3.40 -> v3.40
```

Feature branch naming:

```text
feature/add-login-validation
feature/todo-filter
```

Main branch:

```text
main
```

`main` receives release branches after production deploy succeeds. It represents what has already been released, not every staging candidate.

---

## 9. Monorepo Service Versioning

The app repository contains multiple services:

```text
frontend
user-service
todo-service
```

Each pipeline run still targets one service with the `SERVICE` parameter.

Service image tags carry service identity:

```text
frontend:abc1234-v3.40-staging
user-service:abc1234-v3.40-staging
todo-service:abc1234-v3.40-staging
```

If Git tags are needed later, use service-scoped tags:

```text
frontend/v1.1.0
user-service/v1.2.0
todo-service/v1.6.0
```

But the first Jenkins design can work without Git tags. The release branch name gives the release version, and the commit SHA gives traceability.
